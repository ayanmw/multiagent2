## 一、M0 评审结论（是否符合预期）

**总体判定：出口标准（Web 选模型流式对话）达成，但「企业级 CodeAgent」仍只是单轮问答壳，存在 1 个 P0 + 1 个 P1 真实缺陷，工具/多 Agent/记忆三大能力完全缺失。**

### ✅ 做得好的（扎实）
- **可编译可测试**：`go build/vet/test ./...` 全绿，E2E 集成测试覆盖「注册→建 Provider→sync→启用→SSE 流式→历史持久化」全链路。
- **分层清晰**：api / repo / model / engine / middleware / crypto 边界明确，engine 层收敛了 trpc-agent-go，框架升级只改本层。
- **安全基础到位**：Provider APIKey AES-256-GCM 加密落库且从不回显；APIKey 走 SHA256 不可逆哈希；跨用户越权（Provider/Session）有 `user_id` 归属校验；前端 Markdown 渲染 `html:false` + DOMPurify 双重防 XSS。
- **SSE 流式正确**：`agent.WithStream(true)` 真正逐字增量；AG-UI converter 用 `sawDelta` 标志避免流式终帧 `Message.Content` 重复累加（小细节处理得很对）。
- **工程化意识**：prompt/LEARNINGS 把踩坑（端口残留、node_modules 清理、Playwright 沙箱隔离、SSE 必须 POST 等）沉淀为可复用知识，这正是 Loop Engineering 的「Skills」雏形。

### ⚠️ 问题与风险（按严重度）

**P0 — 多轮对话历史未回灌模型（核心功能缺陷）**
- `engine.go:60-63` 每次请求 `engine.New` 新建 `runner.NewRunner`，框架自动挂**内存版会话服务**，不跨请求保留。
- `sse.go:115` / `chat.go:83` 只传 `model.NewUserMessage(message)` 单条，**DB 里的历史（ListSessionMessages）从未加载给 LLM**。
- 后果：模型视角每条消息都独立单轮，第二句就失忆。DB 历史仅用于前端回放，不影响回复。`ChatView.vue:182` 注释已自认此事实。
- 影响：作为「CodeAgent」不可用——不能基于前文改代码、不能连续推进任务。

**P1 — RBAC 权限矩阵形同虚设**
- `middleware/auth.go` 的 `RequirePermission(resource, action)` 已定义，但 `main.go` 全程未用；仅 `/admin/roles` 用了 `RequireRole(RoleAdmin)`。Provider/Session 写操作仅靠 owner-scoped uid 校验，权限系统是死代码。

**P1 — SessionKey 跨用户可碰撞**
- `repo/session.go:13-31` `GetOrCreateSession`：用户 B 复用用户 A 的 session_key 会新建一行**相同 key**（靠 `AND user_id` 不越权读，但破坏唯一性、混淆审计）。应加 `UNIQUE(user_id, session_key)`。

**P2 — 重复逻辑 / 硬编码 / 小隐患**
- delta 累加规则在 `engine.Chat`（engine.go:99）与 `aguiConverter.Convert`（sse.go:164）各实现一遍，应抽公共函数。
- 魔法值：`engine.go:73` 90s 超时、`auth.go:92` `user.RoleID = 3` 硬编码角色 id（应查 `RoleDeveloper`）。
- SSE 把 `message` 放 GET query（sse.go:40），明文易进访问日志，应改 POST body。

### 企业级缺口（M1 必须补）
| 能力 | M0 现状 |
|------|---------|
| 多轮记忆 | ❌ 仅前端回放，模型单轮 |
| 工具系统 | ❌ 仅 echo/get_time 玩具 |
| 代码执行 / 工作区 | ❌ 无 |
| 多 Agent 协作 | ❌ 单 llmagent |
| Goal 循环 / 自主推进 | ❌ 无 |
| 斜杠命令 | ❌ 无（前端 /clear 是硬编码） |

**M0 完成度评分：4/5** —— 骨架与基础设施优秀，但离「能干活的企业级 CodeAgent」还差一个 M1。

## 二、M1 整体规划（CodeAgent 核心）

> 目标：把平台从「单轮问答壳」升级为**能绑定工作区、能执行代码、能多 Agent 协作、能围绕 Goal 持续循环的 CodeAgent**。
> 对齐 V0.2 里程碑：M1 = 工具+权限、CodeTeam、斜杠命令 + Goal 契约 + CycleAgent + 熔断 + 工作状态文件。

### 2.1 设计原则
1. **先修 P0/P1 再上新能力**：M1-01/02/03 把 M0 真实缺陷补掉，否则新能力建立在沙子上。
2. **Executor 抽象隔离执行安全**：所有代码执行走统一 `Executor` 接口，M1 实现 `HostExecutor`（工作目录约束 + 危险命令策略），Docker 沙箱留 M3 接口预留。
3. **多 Agent 先串行后并行**：M1 的 Coder/Reviewer 由 Orchestrator 串行驱动（同一 workspace），worktree 隔离留 M2，避免并发踩踏。
4. **Goal 只装在 Orchestrator**：规避框架限制（goal 扩展不能与并行工具同用），并行度由 M2 的 taskrun 扇出承担。
5. **护栏三件套前置**：MaxLLMCalls/MaxToolIterations/MaxRetries 从 M1 就配，为 M4 无人值守铺路。

### 2.3 M1 出口标准（验收点）
在 Web 上能：**选模型 + 绑定 workspace → 多轮对话有记忆 → 用 /run 执行 shell → Coder/Reviewer 协同完成一个小任务（写函数并 review）→ Goal 循环持续推进到 complete → 斜杠命令可用 → 刷新后历史仍在。**

### 2.4 技术要点与框架风险
- **持久化 SessionService**：优先用框架 `session` 包（文档称有 SQLite 后端）。若 v1.10.0 该后端签名不友好，退化为「后端加载 DB 历史 → 构造 `[]model.Message` 多轮传入 Runner」——二选一，M1-01 实际开发时定。
- **goal 扩展与并行工具冲突**（框架限制）：Goal 只装 Orchestrator，单 Agent 内不开 EnableParallelTools；并行靠 M2 taskrun 扇出。
- **框架版本锁定 v1.10.0**：所有框架 API 调用收敛在 `internal/engine` 与 `internal/agent`（新增），业务不直连框架。

### 2.5 与后续里程碑的关系
- **M2 生态**：MCP 管理中心 + Skills 仓库 + Git 集成 + **taskrun 后台任务 + Worktree 隔离 + toolsearch 延迟工具箱**（解决 M1 多 Agent 同目录踩踏）。
- **M3 企业化**：可观测/审计/配额 + 预算护栏（token/费用暂停线）+ 人工检查点 + artifact 存储。
- **M4 自主化**：Automation 触发器（cron+Webhook）+ Channel 层 + 跨天恢复 + 无人值守 Loop。
- **M5 进化**：CLI + Knowledge RAG + evolution 技能飞轮 + evaluation 回归 + promptiter + A2A 对外。
