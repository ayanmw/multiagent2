> 状态：待评审 | 日期：2026-07-28 | 前置文档：01-需求与规划.md

## 1. 框架能力全景盘点（V0.1 方案用到 vs 未用到）

### 1.1 V0.1 已覆盖 ✅
| 模块 | 用途 |
|------|------|
| Runner / LLMAgent / Chain / Parallel / Graph | 多 Agent 编排基础 |
| tool（function/file/mcp/agenttool） | 工具生态 |
| session / memory（SQLite 后端） | 会话与记忆持久化 |
| telemetry（OpenTelemetry） | 可观测 |
| model 三协议抽象 | Provider/Model 管理 |
| skill（SKILL.md 仓库） | 技能管理（仅基础） |

### 1.2 V0.1 遗漏、必须补上的核心能力 ⚠️

| 模块 | 能力 | 对 24h 自主平台的价值 |
|------|------|----------------------|
| **goal 扩展** | 会话级目标契约：`get_goal/create_goal/update_goal` 工具注入；模型过早给 final response 会被拦截，强制继续推进直到 `complete` 或 `blocked` | **自主循环的灵魂**。这就是「不满足于一次 ReAct 回合，围绕大目标持续推进」的框架级实现，配 `WithMaxRetries/WithMaxLLMCalls/WithMaxToolIterations` 做运行级熔断 |
| **agent/taskrun** | 后台任务控制面：`start/list/get/wait/cancel_task_run` + `read_task_run_transcript`；每个子任务独立 child session、有 run id、可查进度（事件数/工具调用数/token 数）；FileStore 持久化 | **子代理工程化**。父 Agent 可派生可跟踪、可取消的后台任务；这是「一个产出一个挑错」且互不阻塞的正确形态，远比同步 AgentTool 高级 |
| **CycleAgent** | planner + executor 显式循环至终止条件 | 循环工程的内置原语，V0.1 只列了 Chain/Parallel/Graph |
| **evolution** | 后台异步审查已结束 session → 提取可复用 SKILL.md → 质量门控 → 人工审批 → 发布为托管技能 → 后续运行 warm-start | **平台会越用越聪明**。跑过的任务自动沉淀为技能，这是超越 Claude Code 的差异化能力 |
| **openclaw runtime 模式** | Channel(入口) → Gateway(标准化/allowlist/串行锁) → Runner(执行) → 运行时服务(Cron/Admin/Upload) 四层长运行架构 | 24h 常驻运行时的**参考架构**，直接借鉴其分层与稳定 session_id 设计 |
| **cron 服务** | 常驻调度、持久化定时任务、触发 Agent、结果经 outbound router 回发 | **Automations 触发器**的框架级实现 |
| **codeexecutor / codeact** | 统一代码执行抽象（含交互式 InteractiveProgramRunner）、CodeAct 模式（模型写代码作为行动） | 我们的 Executor 双模式（Host/Docker）应实现此接口而非自造；CodeAct 是比 JSON 工具调用更强的行动范式 |
| **artifact** | 版本化产物存储（内存/S3/COS） | 报告、diff、构建产物的规范存储 |
| **knowledge** | RAG：源加载→向量化→检索 | 项目知识库（V0.1 放 P1，维持） |
| **evaluation / promptiter** | 评估集+可插拔指标+多次运行；GEPA 反射式 Prompt/技能优化 | 回归测试 Agent 质量；自动优化 Prompt |
| **plugin/toolsearch** | 命名空间工具箱 + 语义工具搜索 + MCP 动态工具箱（`mcp__<server>__<tool>`），双工具模式 tool_search + call_tool | 工具多了以后避免 context 爆炸的**延迟工具加载**方案 |
| **AG-UI / A2A server** | 标准 Agent-UI 协议（SSE，CopilotKit/TDesign Chat 客户端）；Agent 间互操作协议 | 前端事件协议可直接采用 AG-UI 而非自定义 SSE；A2A 让平台对外输出 Agent 服务 |
| **humaninloop 示例** | 人机协作确认流 | 危险操作确认机制的参考实现 |
| **dynamic-workflow / AgentFactory** | 按请求动态构造 Agent（不同 prompt/model/工具/沙箱） | 多租户、按任务定制 worker 的正确方式 |

## 2. 方案「不够先进」的部分 — 自我批判

| # | V0.1 的问题 | 升级方案 |
|---|------------|----------|
| P1 | **本质仍是「人发消息→Agent 回复」的被动模式**，没有自主循环 | 引入 **Loop Engine**：Goal 契约 + CycleAgent + taskrun，任务不是「回答完就结束」而是「推进到 complete/blocked 才停」 |
| P2 | **自定义 SSE 事件协议**，重复造轮子 | 直接采用框架 **AG-UI 协议**（内置 SSE server），前端用兼容客户端，省一层转换且天然对齐框架事件模型 |
| P3 | **多 Agent 在同一工作目录**，并发会互相踩踏 | 引入 **Worktree 隔离**：每个 taskrun 分配独立 git worktree，完成后 merge/PR 回主分支 |
| P4 | **斜杠命令触发是唯一入口** | 借鉴 openclaw 四层架构，增加 **Channel 层**：Web/CLI 之外支持 Webhook（CI 失败、GitHub Issue/PR 事件）、定时器、邮件/IM 等入口，全部经 Gateway 标准化后进同一 Runner |
| P5 | **Automations 缺失** | 新增 **Automation 服务**（基于框架 cron + 事件触发器）：定时（每天扫 CI 日志）或事件（Issue 打标签）自动启动 Loop |
| P6 | **Skills 只是「可管理」**，没有生命周期 | 升级为 **Skill 飞轮**：手工编写 + evolution 自动提取 + 质量门控 + 人工审批发布 + warm-start 复用 + promptiter 持续优化 |
| P7 | **Memory 只是会话持久化** | 增加**工作状态外置**：每个长任务维护 `PLAN.md/PROGRESS.md/LEARNINGS.md`（artifact 存储），跨天恢复时 Agent 先读状态文件再继续——这是 Loop Engineering 的「状态记忆」 |
| P8 | **工具全量注入 context** | 采用 plugin/toolsearch 延迟工具箱，MCP 工具按需语义检索加载 |
| P9 | **无预算与安全护栏的长循环很危险** | Loop 护栏三件套：①运行级熔断（MaxLLMCalls/MaxToolIterations/MaxRetries）②平台级 token/费用预算（框架没有，我们在 Runner 外围实现，超预算暂停并通知）③人工检查点（关键节点 human-in-the-loop 审批后继续） |
| P10 | **没有质量回归** | evaluation 模块建立 Agent 评估集，每次改 Prompt/模型/编排跑回归 |

## 3. 升级后的目标架构：Autonomous Loop Platform

```
触发层（Triggers）
  ├─ 人工：Web 对话 / CLI / 斜杠命令
  ├─ Automation：cron 定时（每天 9:00 扫 CI 失败日志）
  ├─ 事件：Webhook（GitHub/GitLab/CI/Jira）、邮件、IM
  └─ Agent 自触发：上一轮 Loop 留下的 follow-up 任务
        ↓
Gateway（标准化 · allowlist · 稳定 session_id · 每会话串行锁）
        ↓
Loop Engine（核心新增）
  ├─ Goal 契约：目标不完成不允许过早收尾（goal 扩展）
  ├─ 计划外置：PLAN.md / PROGRESS.md / LEARNINGS.md（artifact）
  ├─ 子任务派生：taskrun 后台 run（独立 child session + run id）
  ├─ Worktree 隔离：每个 run 独立 git worktree
  ├─ 护栏：熔断 + 预算 + 人工检查点 + 危险操作确认
  └─ 收尾：PR/报告产出 → 通知 → 留存 follow-up
        ↓
Agent 编排（LLMAgent/Chain/Parallel/Cycle/Graph + AgentFactory）
  典型 CodeTeam：Orchestrator → Planner → Coder(worktree A)
                 ⇄ Reviewer(只读，独立视角) → Tester → 回环
        ↓
能力层：tool + toolsearch 延迟工具箱 + MCP Connectors
        + Skills（evolution 飞轮） + Knowledge RAG + codeexecutor(Host/Docker)
        ↓
底座：session/memory/artifact（GORM·SQLite→PG） + telemetry(OTel)
      + evaluation 回归 + AG-UI/A2A 对外协议
```

## 4. Loop Engineering 六要素 → 平台实现映射

| Loop Engineering 要素 | 平台实现 | 框架依托 |
|----------------------|----------|----------|
| 自动化触发器 Automations | Automation 服务：cron 表达式 + Webhook 事件规则 → 自动创建 Goal Session 启动 Loop | openclaw cron 服务模式 |
| 隔离工作区 Worktrees | Workspace 下每 taskrun 自动 `git worktree add`，完成后 diff→PR/merge，冲突交 Reviewer 处理 | taskrun + 自研 worktree 管理器 |
| 技能文件 Skills | SKILL.md 仓库（共享+私有多根目录、HTTP zip 分发）+ evolution 自动提取审批发布 | skill.NewFSRepository + evolution |
| 连接器 Connectors | MCP 管理中心（stdio/SSE/StreamableHTTP）+ 延迟工具箱；预置 GitHub/GitLab/Slack 类连接器模板 | tool/mcp + plugin/toolsearch |
| 子代理 Sub-agents | 三种委托语义分级：agenttool（同步专家）/ transfer_to_agent（交接）/ taskrun（后台可管 run）；Coder 与 Reviewer 强制分离、Reviewer 只读工具集 | agenttool / sub-agents / taskrun |
| 状态记忆 Memory | 三层：session（对话）+ memory 服务（跨会话事实）+ **工作状态文件**（PLAN/PROGRESS/LEARNINGS，重启后先读再续跑） | session + memory + artifact |

## 5. 超越基础 ReAct 的行动范式（按任务复杂度分级）

1. **L1 ReAct**：单 LLMAgent + 工具循环 —— 快问快答
2. **L2 Plan-Execute**：Planner 产出计划外置 → 逐项执行更新 PROGRESS —— 中型任务
3. **L3 CodeAct**：模型直接写代码作为行动（codeact 模式），比 JSON 工具调用表达力强一个量级 —— 数据处理/批量操作
4. **L4 Goal Loop**：Goal 契约 + Cycle/Graph 回环 + taskrun 扇出子任务 + Worktree 并行 —— 「今晚把这个 issue 列表清完」
5. **L5 Autonomous**：Automation 触发 + 跨天状态恢复 + evolution 技能沉淀 + evaluation 回归 —— 无人值守持续运营

平台按任务自动/手动选择层级，L4/L5 强制启用护栏三件套。

## 7. 风险与对策

| 风险 | 对策 |
|------|------|
| 长循环失控烧钱 | 预算硬顶（按 Session/Automation/用户三级），超线暂停待人工恢复 |
| 无人值守写坏代码 | Worktree 隔离 + 只出 PR 不直接 merge 主分支 + Reviewer 独立子代理 + 危险命令确认策略（无人值守时默认拒绝并记录） |
| goal 扩展与并行工具冲突（框架限制：不可开 EnableParallelTools） | Goal 只装在 Orchestrator 上；并行度由 taskrun 扇出承担，不在单 Agent 内并行 |
| taskrun inprocess 单进程限制 | 首期单进程够用；预留 taskrun.Controller 接口，未来多节点自实现（外部队列+lease） |
| 框架迭代快（1800+ commits） | 锁定版本 + engine 层封装隔离，框架 API 变更只改 engine 层 |
